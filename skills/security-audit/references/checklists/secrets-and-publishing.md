# 秘密情報とリポジトリの公開のチェックリスト

★ = 一般に見落とされがちな項目。手順は `skills/pre-publish-secret-scan/SKILL.md`。

## 秘密情報

- [ ] git の **全履歴・全ブランチ** を gitleaks で検査した（`--log-opts="--all"`、`--redact`）
- [ ] 作業ツリーも検査した。検出がビルド成果物（`.next/` など）なら、gitignore 済みで一度もコミットされていないことを確かめた
- [ ] 管理対象の `.env` 系は `.env.example` だけ
- [ ] ★ 親ディレクトリなど、別のリポジトリの管理下に秘密情報のファイルが置かれていない（`git check-ignore -v` で確認）
- [ ] ★ Dockerfile で `COPY . .` するなら `.dockerignore` で `.env*` を除外している（中間レイヤーに残る）
- [ ] プロジェクト固有の鍵の形式（例: `app-` で始まる Dify の API キー）も、パターンを指定して検索した
- [ ] ビルド済みのクライアント JS に鍵が入っていない

## 公開・非公開の扱い

- [ ] ★ 公開リポジトリに、修正前の脆弱性の詳細（Issue、PR、コミットメッセージ）を書いていない
  - 修正作業は非公開リポジトリか GitHub Security Advisory の一時的な非公開フォークで行い、修正を出してから公開する
- [ ] ★ 本番がどのリポジトリからデプロイされているか確認した。非公開側でマージしても、本番に反映されていないことがある
- [ ] 公開側への反映は、force なしの通常の push（早送り）で行う。事前に名義と、公開側が動いていないことを確かめる
- [ ] 公開後、本番の挙動を読み取りのリクエストで確認した

## もし漏れていたら

1. まず鍵を無効化・再発行する（履歴を書き換えても、既に取られた写しは消えない）
2. 利用者の承認を得てから履歴を書き換える（`git filter-repo`）
3. 書き換え後に再スキャンする
