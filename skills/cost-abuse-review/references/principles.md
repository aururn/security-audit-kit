# Agent Instructions: セキュリティ監査と修正

この文書は、AI コーディングエージェント（Claude Code、Codex など）が Web アプリの脆弱性を
調べて直すときの共通ルールです。ツール固有の補足は `CLAUDE.md` などに置き、ルールの正本は
この文書とします。

手順の詳細は `skills/` 以下、確認項目は `checklists/` 以下を正本にします。ここには
「どの作業にも共通する判断の基準」だけを書きます。

## このキットの URL を渡されたとき

利用者がこのリポジトリの URL を貼って、監査やレビューを頼んだときの進め方です。
利用者の環境（`~/.claude`、`~/.codex` など）には何も入れません。

1. このキットを一時ディレクトリに clone する
   `git clone --depth 1 https://github.com/aururn/security-audit-kit.git "${TMPDIR:-/tmp}/security-audit-kit"`
2. 頼まれた内容に合う skill の `SKILL.md` を、clone した中から読み、その手順に従う
   - 脆弱性を調べる、レビューする：`skills/security-audit/SKILL.md`
   - 公開する前に秘密情報を確かめる：`skills/pre-publish-secret-scan/SKILL.md`
   - 見つかったものを直す：`skills/security-fix-workflow/SKILL.md`
   - 高額請求にならないか確かめる：`skills/cost-abuse-review/SKILL.md`
3. 対象の指定がなければ、利用者が今作業しているリポジトリを対象にする

plugin として入れるかどうかは、利用者が決めます（`README.md` の「使い始める」）。

## 基本原則

1. **読んで終わりにしない。再現できるものは再現する。**
   コードを読んで疑わしいと思ったら、ローカルで実際に試して確かめる。上流 API（LLM、SaaS）を
   呼ぶアプリなら、リクエストを記録する偽の上流サーバーを立て、アプリ経由で何が届くかを見る。
   「届くはず」と「届いた」は別物として報告する。
2. **本番には攻撃的なリクエストを送らない。**
   本番に送ってよいのは、状態を変えず、課金も発生させない読み取りのリクエストだけ
   （ヘッダ、Cookie 属性、静的ファイルの有無と大きさ、Dify などに届く前に弾かれることの確認）。
   DAST（ZAP など）や負荷のかかるスキャンは、ローカルか検証環境にだけ向ける。
   動的な確認を始める前に、対象ごとに試してよい URL と読み取りだけの URL を `templates/scope.md` に書き、
   利用者の承認を取る。書いていない URL には送らない。
3. **修正はテストで証明し、テストを壊して検出力を確かめる。**
   修正を一時的に無効にしてテストが落ち、戻すと通ることを確認する。落ちなければ、そのテストは
   修正を守っていない。テストデータは「検証したい規則だけ」で弾かれるように作る
   （別の検証で先に弾かれるデータでは、目的の規則を確かめられない）。
4. **独立したレビューを通す。**
   実装したエージェントとは別のレビュアー（別エージェント、`codex review`、`/security-review`）に
   差分を見せる。P0/P1 を残して完了にしない。妥当な P2 も直し、直さない場合は理由を残す。
5. **脆弱性の詳細を公開の場所に書かない。**
   公開リポジトリの Issue・PR・コミットメッセージに、攻撃手順やコピペできるペイロードを書かない。
   非公開リポジトリか GitHub Security Advisory を使い、修正を出してから公開する。
6. **ダッシュボードでしか確かめられないことは「未確認」と書く。**
   支出上限、レート制限、WAF、LLM プロバイダの利用上限、デプロイ元のリポジトリなどは、
   コードからは分からない。推測で「設定済み」と書かず、利用者に確認を依頼する。
7. **確認結果には、実際に実行した結果だけを書く。**
   実行していないコマンドの成功や件数を推測で埋めない。

## 監査の進め方（概要）

1. 範囲と脅威モデルを決める：何が公開されているか、誰がお金を払うか（従量課金）、秘密情報はどこにあるか。試してよい URL を `templates/scope.md` に書いて承認を取る
2. 入口を洗い出す：API ルート、Server Actions、Middleware、Webhook、ファイルアップロード、iframe 埋め込み
3. 自動スキャン：`scripts/run-scan.sh`（秘密情報・依存関係・SAST・CI 設定）
4. 手作業のレビュー：`checklists/` をカテゴリごとに当てる
5. 動的な確認：ローカルで再現（偽の上流サーバー）→ 本番は読み取りだけ
6. 報告：重大度・根拠・再現手順・未確認事項を分けて書く

詳細は `skills/security-audit/SKILL.md`。

## 重大度の目安

| 重大度 | 目安 |
| --- | --- |
| Critical | 認証なしで RCE、秘密情報の取得、他人のデータの取得ができる |
| High | 認証なしで課金を発生させ続けられる、API キー付きのリクエストを任意の場所へ向けられる、保存型 XSS |
| Medium | 条件付きで成立する（CSRF、限定的な情報漏洩、休眠中の XSS） |
| Low | 多層防御の不足（ヘッダ、Cookie 属性、不要な公開ファイル） |

「従量課金の上限なし × 認証なし」は、技術的には地味でも実害（高額請求）が大きいので High 以上として扱う。

## 報告の書式

報告は、読み手がすぐ動けるように書く。

- 結論を先頭に置く。1 行目は「最も重大な finding と、その直す方向」。前置き（「〜を調べました」）や経緯から始めない。
- finding は重大度の高い順に並べ、各件を **重大度・場所（`file:line`）・攻撃者は何ができるか・証拠（再現したことと方法）・直す方向** の順で書く。
- 実測と推測を分ける。再現したもの、コードから疑っただけのもの、ダッシュボードでしか確認できないもの（未確認）を、別の一覧にする（基本原則 6・7）。
- 挨拶や締めの一文（「お役に立てば」「ほかにあれば」）を書かない。終わったら終わる。
- 一覧が長いときは、関係するものをまとめ、重大なものから見せる。省くのではなく、順序で示す。

## 修正の進め方（概要）

- 1 Issue = 1 PR。1つの PR には1つの規則だけを入れる
- Issue は予定（要求振る舞い、テスト設計、受け入れ条件）、PR は実装後の振る舞いと実行結果を書く
- 変更するファイルが重ならない単位に分ければ、並列で進めてよい
- CI と独立レビューの両方が通ってからマージする

詳細は `skills/security-fix-workflow/SKILL.md`、書式は `templates/`。

## ツールの扱い

- スキャナも攻撃されうる（2026年3月、Trivy のリリースと GitHub Action のタグが改ざんされた）。
  ツールは版を固定し、公式のチェックサムと照合してから使う。GitHub Actions は commit SHA で固定する。
- 秘密情報のスキャンは、結果に値を出さない設定（`--redact`）で実行する。
- スキャナの指摘は候補であって結論ではない。圧縮済みのベンダーコードやビルド成果物（`.next/` など）の
  誤検出は、根拠を添えて除外する。

## 禁止事項

- 利用者の明示の承認なしに、本番への DAST・負荷試験・大量リクエスト、force push、履歴の書き換え、
  リポジトリの公開範囲の変更、秘密情報のローテーションを行わない
- 秘密情報の値をログ、報告、Issue、PR、テスト成果物に出さない
- 公開リポジトリへ、修正前の脆弱性の詳細を書かない
